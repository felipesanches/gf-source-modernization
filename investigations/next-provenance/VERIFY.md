## Verdict

The provenance findings hold up. Lohit's METADATA commit a403c9b is another family's tag, and the FFTM stamps pin Bengali to 0df83ad and Tamil to 361b23b. Thabit is the build.py output: the 2010 .sfd plus Thabit.fea, IBM Courier and the X.Org AFMs, with generated obliques. Yellowtail's '.sfd' is a Type 1 PFB. I checked every FontForge-exporter rule the agent cites against the eb711fd7 sources, and every babelfont reader defect is still present on upstream main 91bf8bb.

The report overstates what lands. Four functional gaps are missed, and each is hidden by the table gate:
1. **U+00A0.** All four Thabit styles gain U+00A0, from a glyph that exists only in the 2010 save. land.py's exact-codepoint check refuses it. A documented dropglyph edit fixes it (verified).
2. **The obliques are not italic.** Both lose the ITALIC style bit and are named like the uprights, because build.py's naming step and FontForge's name-derived italic are not reproduced.
3. **USE_TYPO_METRICS.** The converter sets it for OS/2 v1 releases where FontForge did not. That changes line spacing, markedly for Lohit-Tamil, which the agent calls landable and 0/0.
4. **The Bengali marker already exists.** The 'cheaper partial fix' for Lohit-Bengali is already in babelfont, but mis-cased ('# Automatic code start'). Fixing the string is the first upstream step and reproduces the agent's 284 -> 117 words.

Other revisions:
- The spacing-combining PR must also change SetSubcategory, which the recipe always runs.
- implied-oncurves models only one of FontForge's two numbering paths.
- The copyright edit does not reproduce the release string.
- mergepsfont's worth-outputting test is not FontForge's.

Nothing new is landable. At best, Lohit-Bengali and Lohit-Tamil are table-clean after re-pairing, and neither is functionally equivalent yet. Thabit needs the uni00A0 drop, the oblique naming and italic work, and the Latin SplineSetsTTFApprox port (or a decision) on top of everything the agent listed.

## Per edit

- [keep] Merge Thabit.fea into the source, as build.py does -- Verified. build.py merges the feature file before the fonts (font.mergeFeature(fea), then font.mergeFonts). FontForge 2008's fea_ParseLookupFlags accepts the comma-separated 'RightToLeft, IgnoreMarks', so ligaLamAlef gets flag 9. The release's GSUB is 5 arab lookups with flags 1,1,1,1,9 plus the latn liga, and PfEd names them '<name>' / '<name> subtable'. My w2 build reproduces the GSUB lookup for lookup (runs/w2/Thabit.layout.txt vs runs/thabit_release_layout.txt). The op still has to be added to tools/sfd_edit.py.
- [keep] Add the IBM Courier AFMs FontForge read beside cour/*.pfa -- Keep as decision D3. It is inferred, but the inference holds. In FontForge 2008, SCLigDefault is commented out (fvfonts.c:876, splineutil.c:2473), so a liga lookup can only come from an AFM (CheckAfmOfPostscript). I fetched the X.Org 88a51da files myself: the PFAs are byte-identical to hg's, cour.afm has exactly the 5 'L' ligatures and 0 KPX (the release has no kern), and PfEd names the lookup "Courier-'liga' Standard Ligatures in Latin lookup 0".
- [revise] Merge IBM Courier into the source, as build.py does -- The op claims to follow _MergeFont, but its worth-outputting test is 'draws or is referenced'. FontForge's SCWorthOutputting is draws || widthset || anchor || dependents (splinesaveafm.c:1063), so the op drops Courier's blank 'spacenumeric' (600, unencoded). FontForge copied that glyph: the release has 788 glyphs = 308-1+478+3. The gate calls it unreachable, so it does not block, but the op is not exact. Separately, the cu2qu stand-in leaves 60-83 Latin glyph diffs (up to 46 px) and about 148 word diffs per style (runs/w1/SUMMARY.txt). The edit is therefore not yet functionally equivalent (D5).
- [revise] Generate the oblique sources as build.py does -- The ops reproduce the skew and the paste, but not obliqize()'s naming step: fontname+'-Oblique', fullname+' Oblique', familyname, and the Arabic SubFamily name. FontForge 2008 derived macStyle italic from 'Obli' in the name (macbinary.c _MacStyleCode). The release obliques therefore carry fsSelection ITALIC and macStyle 2/3. Our builds come out named 'Regular Medium'/'Regular' and 'Bold'/'Bold', the same as the uprights, with fsSelection REGULAR+USE_TYPO_METRICS or BOLD, macStyle 0/1 and PS names Regular-Medium/Bold-Bold (runs/style_bits_hidden.txt). METADATA wants post_script_name Thabit-Oblique / Thabit-Bold-Oblique and style italic. The gate hides all of this because it accepts OS/2.fs_selection and head.mac_style wholesale and does not gate names. Even with FontName Thabit-Oblique set, babelfont+fontc give fsSelection REGULAR and macStyle 0 (runs/v6-oblique-named/style_flags.txt), so a converter rule (FontForge's name-derived italic) or an explicit style edit is also needed.
- [revise] Credit IBM for the Latin, as build.py does -- The body says 'the release's name ID 0 carries it', but applying the 2010 build.py text to the 2010 copyright does not give the release's string. The edit would give 'Typeface and data (C) 2008-2010, Khaled Hosny.\nThis font ... license.\nLatin glyphs are ...'. The release's name ID 0 is 'Typeface and data (C) 2002-2008, Khaled Hosny.This font is distributed under the terms of OFL license. Latin glyphs are Copyright (c) IBM Corporation 1990,1991.': different years, and a space separator. Either restore the release string and say it comes from the binary, as the FamilyName edit does, or drop the edit as not functional. It is marked unverified and should stay so.
- [keep] Restore the family name Thabit -- Keep as decision D2. The body says the value comes from the release and METADATA, as the rules require. It is incomplete, though: the Regular still gets subfamily 'Medium' (TTFWeight 500), and for the obliques it has to be paired with the missing oblique naming and italic step above.

## Objections

- Lohit-Bengali rendering (converter-fidelity): the class is right but the cause is incomplete. The 'declared abvm suppresses fontc's writer' effect comes from a mis-cased marker babelfont already emits: '# Automatic code start' against fea-rs's case-sensitive '# Automatic Code'. That is a one-line upstream bug, not a missing feature. Only the remaining 117 words need the explicit-lookup design.
- Lohit-Tamil is called landable ('CLEAN, 0 glyph and 0 word rendering diffs'), but it is not functionally equivalent. The build sets fsSelection USE_TYPO_METRICS, while the release (OS/2 v1) does not. FontForge only sets bit 7 when the OS/2 version it writes is 4 or more (tottf.c eb711fd7 lines 3283-3289); babelfont maps OS2_UseTypoMetrics unconditionally. For Tamil, apps that honour the bit switch line spacing from win 866/363 to typo 1400/-648/+20. The table gate hides this by accepting OS/2.fs_selection wholesale. It is a converter-fidelity row; runs/v5-tamil-no-typo-bit shows fs_selection [64,192] goes away when the bit is not set.
- Thabit-Oblique and Thabit-BoldOblique: '3 rows, 2 with land.py's workaround, 0 with the gate change' is only a table-gate result. The generated sources lose the release's ITALIC style bit (fsSelection 1 -> REGULAR+USE_TYPO_METRICS; macStyle 2 -> 0, 3 -> 1) and are named 'Regular Medium' / 'Bold' like the uprights. This is functional (style linking, METADATA style italic and PS name) and is not the 'names; not gated' provenance row. Part of it is provenance (build.py's naming step was not reproduced), and part is converter fidelity (FontForge's name-derived italic).
- Thabit (all four styles), 'rows_after 0 with the gate change': land.py would still refuse every style. The build GAINS U+00A0 (glyph uni00A0, the last glyph, gid 307/309, of both 2010 .sfd files). The release neither encodes nor contains that glyph, so the 2010 save introduced it. The table gate accepts gained codepoints, but land.py's cmap_difference requires the release's exact codepoints. This is a provenance row with no edit proposed.
- Yellowtail: 'google/fonts 1baf54ea4 changed only name IDs 3/4/5/6 and head.modified/fontRevision' is imprecise. The cmap table bytes also changed; the mappings are identical, so this is a re-encoding and functionally irrelevant.

## Missed

- Thabit, Thabit-Bold, Thabit-Oblique, Thabit-BoldOblique: GAINED U+00A0. The agent's own p3 gate prints it ('our uni00A0 (an addition at U+00A0...)') but the report never mentions it. Our builds have 786 glyphs against the release's 788 = 308-1+478+3, and uni00A0 is the only glyph the release lacks. It is empty, Width 637, 'Flags: HW', and last in both .sfd files; nothing refers to it. FontForge 2008 would have exported it (SCWorthOutputting counts widthset), so the release's 2008 source did not contain it. Proposed documented edit: 'Drop uni00A0, which the 2010 save added', a new sfd_edit op dropglyph. Origin: the release's cmap and glyph set, and its position as the last gid. Measured with DROP_NBSP=1 (probes/thabit_pipeline_verify.sh, runs/w2): codepoints become exactly the release's in all 4 styles, with no change to rows or rendering (runs/w1_w2_cmap_exactness.txt).
- Thabit obliques: build.py's obliqize() naming step (fontname/fullname/familyname and the Arabic SubFamily) and FontForge 2008's name-derived italic (macbinary.c _MacStyleCode: 'Obli' -> sf_italic, which becomes fsSelection ITALIC) are not reproduced. Ours is not italic and is named like the upright (runs/style_bits_hidden.txt). Setting FontName Thabit-Oblique alone is not enough; babelfont+fontc still give REGULAR/macStyle 0 (runs/v6-oblique-named). A babelfont rule is needed to mark the instance italic, as FontForge did when the source states no MacStyle.
- A converter-fidelity rule for all FontForge-exported styles with OS/2 version < 4: do not set USE_TYPO_METRICS (FontForge tottf.c: only 'if ( os2->version>=4 )'). It affects Lohit-Tamil (typo 1400/-648/20 vs win 866/363), Lohit-Bengali (750/-274/0 vs 760/325), Thabit and Thabit-Oblique (819/0/900 vs 983/528). It is hidden by table_gate.py ACCEPTED['OS/2']['fs_selection'] ('USE_TYPO_METRICS is set by the build'), even though the conversion, not the build, sets it from a flag FontForge ignored. It is probably programme-wide, beyond this unit.
- babelfont's existing insertion marker is mis-cased: fontforge.rs:3759 '# Automatic code start', upstream Simon 66334a7a, still on main 91bf8bb. fea-rs requires '# Automatic Code'. This one-line fix is the upstream-mergeable first step for Lohit-Bengali, 284 -> 117 words (runs/v2-bengali-marker-casefix). It probably affects every SFD that declares abvm/blwm/mark/mkmk/kern/dist through a chain or other lookup.
- The regression sweeps (probes/sweep_summary.py) compare verdict and row COUNTS only. A patch that closes one row and opens another in the same style is invisible there, as the Cardo-Italic +2/-4 case shows; the 'no table-row regressions' claim is weaker than stated.
- mergepsfont omits Courier's blank 'spacenumeric', which FontForge merged because it is widthset (unencoded, 600). It is harmless (the gate calls it unreachable), but the op does not match _MergeFont.
