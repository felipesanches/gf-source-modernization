# next-fstype -- investigation findings

**Model**: Claude Opus 5.5 (investigating agent, adversarial verifier, and the
conclusion below). Written from the agents' structured results (`results.json`).

## Conclusion

Titillium Web (11 styles) and Wallpoet: fsType is google/fonts' later release edit
(93550bd32, 8ccda7bf7) -> one documented FSType 0 edit per style. Titillium's ExtraLight
styles come from the Thin .sfd, renamed when Google Fonts shipped them (a history-based
pairing rule and documented rename + usWeightClass 275 edits). The verifier found three
converter bugs: the PostScript name is written into the wrong Glyphs property (affects
16 landed styles), head.fontRevision ignores sfntRevision, and every contour's start
point is rotated.

## Investigator's report

Each fix was verified with the unchanged tools/baseline.sh harness: one build per style,
paired by construction from runs/families-fstype.tsv, which is families-next.tsv's 10
rows plus the 2 rule-4 ExtraLight rows. The converter was integration-ff-prs 17ea899 via
BF=probes/bf_with_workarounds.sh, which applies tools/workarounds.py exactly as land.py
does. Candidate .sfd files come from probes/make_candidates.py, which calls
sfd_edit.apply as land.py would and logs each edit's before value. r0 reproduces
baseline-next exactly (Black, Regular and Wallpoet gate texts identical). Stale counts
are unchanged in every run. Across r2/r3/r4 the cmap is exact (no codepoints gained or
lost) and diffenator3 reports 0 glyph and 0 word differences. The whole Titillium family
built from one config.yaml, as land.py does it, gives 11/11 gate 0. fontspector A/B
(1.6.0) shows 0 checks worse on both families.

Rows before: r0 fidelity-only: 12 styles BLOCKING, 21 rows: OS/2.fs_type x12 (Titillium [0, 8] x11, Wallpoet [0, 4]) and OS/2.us_weight_class x9. TitilliumWeb-ExtraLight and -ExtraLightItalic were UNPAIRED in families-next.tsv, so the family could not land.

Rows after: r1 with land.py's weight workaround: 14 rows (fs_type x12, ExtraLight us_weight_class [275, 200] x2). r2 with FSType 0: 10 CLEAN, 2 rows left (ExtraLight weight). r3 with the ExtraLight rename + TTFWeight 275: CLEAN 0. All 12 styles CLEAN. One-config titilliumweb build: 11/11 gate 0. Optional r4 version edit: 11/11 CLEAN, fontRevision 1.002. r5 babelfont PS-name prototype: Wallpoet CLEAN with name ID 6 restored.

Confidence: High for the fsType rows, the weight-class rows and the ExtraLight pairing. Each is tied to a named google/fonts commit (93550bd32, 8ccda7bf7) through byte-level history, FFTM source-modified times match the .sfd states, FontForge's exporter source was read, and every fix was verified with the harness, including the one-config family build. Medium for the babelfont glyphs3 PS-name proposal: the mapping defect and its effect are reproduced, but upstream semantics need Simon's agreement and 11 environment-dependent lib tests were not re-run on the unpatched commit. Wallpoet name ID 4 and one fontspector outline-check status change are unexplained.

## Proposed tool changes

- **tools/pair_next.py (workspace tool)**: Rule 4, which applies only where rules 1-3 leave a shipped font UNPAIRED, so it cannot change an existing pair. Collect name ID 6 from every google/fonts revision of the file (git log --follow) and from the binary the base commit keeps at the same path. If exactly one of those historic names matches .sfd FontNames, pair it by rules 1-2 (-TTF variant preferred) and log the commit that renamed it. Optional corroboration: FFTM.sourceModified equals the .sfd's ModificationTime. Regenerating families-next.tsv then adds TitilliumWeb-ExtraLight <- src/TitilliumWeb-Thin-TTF.sfd and TitilliumWeb-ExtraLightItalic <- src/TitilliumWeb-ThinItalic-TTF.sfd, which is what runs/families-fstype.tsv holds.

  Evidence: runs/pair_by_history.txt: of the 5 UNPAIRED rows in logs/pair_next.log, it pairs exactly the 2 Titillium rows (historic name TitilliumWeb-Thin(Italic) at google/fonts 90abd17b4 and hg 52f780bc9, renamed by 93550bd32, one FFTM stamp throughout).   Upstream: none (workspace tool; Felipe approves the edit to tools/pair_next.py and the regenerated families-next.tsv)
- **babelfont-rs (babelfont/src/convertors/glyphs3.rs)**: Fix the Glyphs 3 name-property mapping. Write names.postscript_name (name ID 6) as `postscriptFontName`, not `postscriptFullName`. Write names.full_name as `postscriptFullName`. Stop writing name ID 20 (the CID findfont name, which has no Glyphs property) as `postscriptFontName`. Map the reader the same way. fontc (glyphs2fontir try_name_id) reads postscriptFontName as name ID 6 and ignores postscriptFullName for the name table, so today an .sfd FontName without a style suffix (Wallpoet, Smythe, NovaCut...) is lost and fontc derives Family-Style. The fix is not FontForge-specific: it affects any conversion to .glyphs.
