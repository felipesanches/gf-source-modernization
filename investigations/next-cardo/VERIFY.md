Largely sound, and the core claims reproduce exactly from my own harness runs and my own build of their prototype. The p2 .glyphs are byte-identical to theirs.

## Objections

- Cardo-Bold 'kern across a combining mark 177/426' is classed compiler-gap (needs fontc ignoreMarks=false). It is closable as converter-fidelity. Two causes co-exist: fontc's IgnoreMarks flag, and the GDEF classes. babelfont leaves the 165 zero-width combining marks uncategorised and fontc's GlyphData makes them marks, whereas FontForge 20110222 gdefclass() exported every glyph as base. A real fontc 1.0.0 build of the p2 .glyphs with FontForge's GlyphClassDef stated as an FEA GDEF prefix closes the row (0/426, GDEF equal, proposed gate 0; runs/emu-bold-ffgdef-fea). The row's cause should name the GDEF classes, and families_landable_after should drop 'needs the fontc ignoreMarks=false change' for Bold.
- The fontc ignoreMarks=false proposal lists Salsa-Regular (landed) as affected, but kern flags are not Salsa's cause. The landed build has no GDEF, so HarfBuzz synthesizes mark classes from Unicode. Flag 0 alone leaves 246/285 kern+mark and 257/282 base+mark. The release's GDEF closes both (runs/salsa_landed_causes.txt).
- 'Cardo-Italic GSUB.* -- gate-arbitration' needs no gate change. The existing arbitrate_gsub_lookup_order already passes it once the nbspwidth source edit is in (s1: 'RELEASE-STALE the same GSUB lookups in a different order; 69696 shaped runs identical'). It is a consequence of the nbsp row, not a gate change.

## Missed

- Cardo-Bold GDEF.glyph_classes: the release has 2992 base glyphs and 0 marks; ours has 165 marks. The gate files it RELEASE-STALE 'correction... disclose', and the unit treated it as background. It is load-bearing: on its own it produces the whole kern+mark difference (simulation: release classes -> 0/426). A converter rule can reproduce it (FontForge gdefclass as an FEA GlyphClassDef, verified by a real build). Glyphs categories cannot: category=Letter makes fontc omit GDEF entirely, and base+mark rises 744 -> 4844.
- The shaping corpus's base+mark+mark set is EMPTY for all three styles. 'Hebrew' counts presentation forms, so it exceeds the 40-base cap, and no stacked cluster was ever shaped. My probes/multimark_compare.py (60909 strings) confirms p3 Regular = 0. It shows lookup order causes 1118 stacked differences at p2, not only 10 strings. It adds 1303 (Bold, all <=1 unit) and 1542 (Italic, 341 over 10 units, worst 13) stacked fallback-positioning differences to the unresolved fallback item (runs/p2/multimark_deltas.txt).
- Landed Salsa-Regular (cb27c62, CLEAN) is not functionally equivalent in base+mark: 257/282 strings differ, e.g. 'B'+U+0300 advances 970 in the release and 636 in ours. Our build has no GDEF, so HarfBuzz zero-widths gravecomb/acutecomb (hmtx 334, class base in the release). This is a pre-existing landed-repo problem, found while checking the unit's Salsa claim.
- Cardo-Italic GDEF ligature class: the release classes 18 glyphs as ligatures. p2 gets 15 of them (the ones with carets); A_R and uniFB4F (.sfd GlyphClass: 3) and f_j (Ligature2) stay unclassed. The gate's GDEF arbitration discusses only marks. This is inert today: no MarkLigPos and no IgnoreLigatures lookup.
- Cardo-Italic has 3 marks that the release classes base (U+0485, U+0486, U+05B9), disclosed by the gate as a correction. Harmless for Latin kern once flag 0 lands, but it is still a fidelity difference nobody states.
- Cardo-Italic glyph names that FEA cannot express, '1E0A' and 'uniA78#' (U+A783). They are harmless now, but they block any FEA-based fix that lists them (including the GDEF route) and should be in the diagnostics proposal.
- Minor inconsistency in the unit's own numbers: unresolved says Bold 746 / Italic 840 base+mark fallback strings, while shaping_summary and rows_after say 744 / 839. My runs give 744 / 839.
- The fallback-offset cause could be stated more precisely. The release's composite glyf headers match none of control box, on-curve box or outline for 81 (Italic), 192 (Bold) and 286 (Regular) composites (probes/composite_bbox_rule.py). Example: Italic uni0312 header yMin 1170 vs outline 1158 vs control box 1133; ours writes the control box, as fontTools does. HarfBuzz fallback reads these headers. FreeType places the outline from the points (probes/stale_lsb_render.py), so the stale bearings do not move rendered glyphs.
