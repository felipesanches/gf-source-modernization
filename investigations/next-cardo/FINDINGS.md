# next-cardo -- investigation findings

**Model**: Claude Opus 5.5 (investigating agent, adversarial verifier, and the
conclusion below). Written from the agents' structured results (`results.json`).

## Conclusion

Cardo needs a glyph rename (a digit-initial name fea cannot express), one advance edit,
babelfont fixes (insertion-marker spelling, ligature carets, spacing marks, lookup
precedence, no anchor propagation) and a fontc option (KernFeatureWriter ignoreMarks,
Italic only). googlefonts/CardoFont is archived: where to land it is Felipe's call. The
verifier also found the table gate hides advance changes and passes landed families that
shape differently (Italiana double kerning, Salsa without GDEF).

## Investigator's report

All three pairs come from the pipeline's own pairing (families-next.tsv), and each is
exact. Every .sfd's CreationTime and ModificationTime equal the release's FFTM
sourceCreated and sourceModified, and the glyph counts are equal: 3845, 2993 and 2387
(runs/cardo_release_history.txt). Every stage ran the harness (tools/baseline.sh through
probes/run_stage.sh), then both the shared gate and the proposed gate, then a HarfBuzz
shaping comparison on absolute glyph positions (probes/shaping_compare.py). Only the
shaping comparison catches the GPOS problems the gate waves through. Stages: r0 baseline
(integration converter); r1 Regular rename; s1 Italic nbspwidth and Bold with land.py
workarounds; p1 prototype babelfont; p2 plus --fontforge-no-anchor-propagation; p3
Regular with the emulated lookup placement; p2-sim-kernflag0 (fontc ignoreMarks=false
simulated).

Rows before: Cardo-Regular: BUILD-FAILED (FEA parsing failed with 2 errors). Cardo-Italic: shared gate 10 blocking (proposed gate 11: +hmtx.uni2E11, +hmtx.uniF15B, -dirhint). Cardo-Bold: shared gate 2 (head.font_direction_hint, OS/2.us_weight_class). Shaping at r0/r1: Regular 4361/181328 base+mark and 45/45 d3 words differ; Italic kern+mark 2056/3057; Bold kern+mark 177/426.

Rows after: Cardo-Regular: p2 shared gate 1 (head.font_direction_hint), proposed 0, shaping 10 base+mark and 7 words. p3 (emulated lookup placement): shared 1, proposed 0, shaping 0 in every corpus. Cardo-Italic: s1 (nbsp edit, integration converter) shared 6 / proposed 7; p2 shared 3 (GDEF.glyph_classes, GDEF.mark_glyph_sets, dirhint) / proposed 2, lig carets equal (15), 0 advance differences; with simulated flag-0 kern, shared 1 / proposed 0, kern+mark 0/3057. Cardo-Bold: s1/p2 shared 1 / proposed 0; kern+mark 177/426, 0 with simulated flag-0 kern. Base+mark fallback offsets (Bold 744, Italic 839) are unchanged and remain unresolved.

Confidence: High for the build failure (full diagnostic plus a minimal repro that fails in fontc and feaLib and builds after the rename), the nbsp edit (binary diff of d70318ab8), the lig carets, the advancing marks, the font_direction_hint rule (FontForge source at 10 tags plus an oracle matching 147 of 149 releases) and the marker bug (fea-rs source plus the fontc warning plus shaping 4361 -> 956). High that GPOS lookup order is the whole residual Regular difference (a two-way reorder test on the release). Medium for the two changes that were not built: lookup placement was emulated on the .glyphs and then really compiled, and fontc ignoreMarks=false was simulated by editing built fonts. Every probe has a docstring and every run output is under investigations/next-cardo; nothing was committed.

## Proposed tool changes

- **babelfont-rs**: Write the feature-writer insertion marker as '# Automatic Code' (ufo2ft INSERT_FEATURE_MARKER spelling) instead of '# Automatic code start' in convertors/fontforge.rs (the abvm/blwm/kern/dist/mark/mkmk blocks). With the current spelling fontc and ufo2ft treat those features as hand-written and generate no mark/mkmk/abvm/blwm lookups from the converted anchors. babelfont's own subsetlayout.rs already tests for '# Automatic Code'.

  Evidence: fea-rs 1.0.0 typed.rs has_insert_marker uses starts_with("# Automatic Code"). The fontc warning 'Skipping generating feature mark' is reproduced. Cardo-Regular: base+mark shaping differences 4361 -> 956 of 181328. probes/automatic_code_marker.py: in the next batch it affects Cardo-Regular (mark) and Lohit-Bengali (abvm); no landed repository (kern is exempt because glyphs-reader appends the marker to a manual kern feature). Regression check: Italiana, Sanchez x2, Lohit-Bengali and Lohit-Tamil keep their gate verdicts and shaping counts (runs/reg-proto).
  Upstream: babelfont-rs (simoncozens): one-line fix to code from upstream commit 66334a7; Felipe files it.
- **babelfont-rs**: FontForge reader: turn LCarets2 into Glyphs caret_1..caret_n anchors (x = caret, y = 0) on every foreground layer, following FontForge's GDEF writer: non-zero carets only unless LigCaretCntFixed is set, ascending, or descending for a right-to-left glyph. Also parse LigCaretCntFixed.

  Evidence: Cardo-Italic GDEF.lig_carets row closes: 15 LigGlyphs equal to the release (runs/p2-proto). FontForge v20110222 tottfgpos.c LigCaretCnt/DumpLigCarets and sfd.c LigCaretCntFixed. probes/lcarets_census.py: Cardo-Italic is the only style in either batch with exportable carets.
  Upstream: babelfont-rs (simoncozens): new PR.
- **babelfont-rs**: An advancing mark is 'Spacing Combining', not 'Nonspacing'. The SFD reader (GlyphClass 4 with a non-zero Width) and the --set-subcategory filter (a mark with an _anchor and a non-zero advance in any layer) both set it. A Glyphs compiler exports a Nonspacing mark zero-width (glyphs2fontir 1.0.0 source.rs:1828); a SpacingCombining mark keeps its advance and stays GDEF class 3. The reader half is the next-provenance unit's babelfont-spacing-combining-mark.patch; the set-subcategory half is new here, because that filter overwrote the reader's value for marks with anchors (Cardo-Regular uni0304 and uni05B105BD).

  Evidence: Italic: 6 hmtx rows close (2 of them hidden by the gate). Regular: 2 hidden rows close. Lohit-Tamil u0BC1 and u0BC2 close (runs/reg-proto: 8 -> 6 rows). 0 advance differences in all three Cardo p2 builds. Side effect: fontc's kern writer then uses a mark filtering set over these marks (Italic GDEF.mark_glyph_sets row); see the fontc change below.
  Upstream: babelfont-rs (simoncozens): one PR, or fold it into the next-provenance unit's PR.
- **babelfont-rs**: Keep FontForge's lookup precedence around compiler-generated lookups. For a feature that carries the insertion marker, define the lookups that only this feature references after the marker, inside the feature block, rather than in featurePrefixes. fea-rs then inserts the generated mark-to-base lookups before them (InsertionPoint = next_gpos_id() at the marker) instead of after every lookup the file defines. A lookup used by another feature or by a contextual lookup stays in the prefix.

  Evidence: Cardo-Regular with every other fix still differs in 10 base+mark strings and 7 diffenator3 words (Hebrew cantillation over vowels). probes/lookup_order_test.py shows the order is the whole cause, and that the release's MarkBasePos lookups placed first shape identically to the release (0/241128). probes/mark_lookups_after_marker.py applies this layout to the converted .glyphs, and a real builder3 e851b8b / fontc 1.0.0 build of it gives 0 differences in every corpus and proposed gate 0 (runs/p3-marks-first). This is EMULATED on the .glyphs, not implemented in Rust. The general case (FontForge interleaving that marks-first does not reproduce) would need explicit FEA mark lookups in .sfd order.
  Upstream: babelfont-rs (simoncozens): design change to discuss with Simon before a PR.
- **fontc**: Honour ufo2ft's KernFeatureWriter option ignoreMarks=false (featureWriters userData) instead of rejecting it as unsupported. fontbe already has the path (KernSplitOptions.ignore_marks / make_lookups). Companion babelfont change: when a FontForge source's kern lookups carry no IgnoreMarks flag, write that featureWriters option into the Glyphs userData, so the kern lookup keeps FontForge's flag 0 and gets no spacing-mark filtering set.

  Evidence: fontir 1.0.0 feature_writers.rs:197-200 hard-errors on 'KernFeatureWriter ignoreMarks=false'; fontbe kern.rs:1130 has the branch. Simulated with probes/simulate_kern_flag0.py on the p2 builds: Italic shared 3 -> 1 and proposed 2 -> 0 rows; kern+mark shaping Italic 2056/3057 -> 0 and Bold 177/426 -> 0. probes/kern_scan.sh (runs/kern_scan.tsv) finds kern-across-mark differences in 5 of the 126 builds kept in scratch: Cardo-Bold, Cardo-Italic, Salsa-Regular (246/285, landed CLEAN), Poly-Regular (2), Varela-Regular (4).
  Upstream: fontc (googlefonts/fontc): feature parity with ufo2ft, needs an issue or PR; then babelfont-rs for the userData entry. Felipe files both.
- **babelfont-rs**: Recipe fidelity flag --fontforge-no-anchor-propagation (the Glyphs custom parameter 'Propagate Anchors' = 0): FontForge exports only a glyph's own anchors. The filter is the next-provenance unit's prototype, applied unchanged; it has to be registered in filters/mod.rs and passed by tools/recipe.py for FontForge sources.

  Evidence: Cardo-Regular p1 -> p2 (the only change is this flag): base+mark shaping differences 956 -> 10 of 181328 (runs/shaping_summary.txt).
  Upstream: babelfont-rs (simoncozens): owned by the next-provenance proposal.
- **table_gate.py (sfd-batch5/tools, this programme's gate)**: (a) Never hide an advance: expand_overflow also recomputes advances when diffenator3 overflows the hmtx section, and arbitrate_lsb keeps the width part of a row BLOCKING. (c) Replace the structural GPOS acceptance ('legacy kern modernised') with a shaping test such as probes/shaping_compare.py, comparing absolute glyph positions: it passed a build that had lost every mark-to-base lookup.

  Evidence: (a) probes/advance_audit.py found hidden widths in Cardo-Italic (2), Cardo-Regular (2) and Lohit-Tamil (5). (b) The oracle matches 147 of 149 releases (misses: Tuffy x2, which have no FFTM). (c) runs/kern_scan.tsv shows letter-pair kerning differences the gate passed in Italiana-Regular (726/13689, landed CLEAN: FontForge's one lookup holds the same pair in two subtables, e.g. B v -20, and babelfont emitted an FEA lookup plus Glyphs kerning, so ours kerns twice, B 530 against 550), Ultra-Regular (260) and Thabit x2, and Cardo-Regular r1 passed with 4361 base+mark differences. First-batch builds: Kristi-Regular 0->1 and NosiferCaps-Regular 1->2, both from a .notdef advance of 748 vs 1024 (runs/proposed_gate_sweep_first.tsv).
  Upstream: none (programme-internal tool)

  Evidence: Cardo-Regular 10192.04. Repro: probes/fea_digit_glyphname (fontc 1.0.0 and feaLib both reject). builder3 e851b8b -v prints only the count; the fontc CLI prints the location and token.

## Unresolved

- Cardo-Bold 746 and Cardo-Italic 840 base+mark strings (of 134629 and 136246) place the mark differently under HarfBuzz fallback mark positioning (neither font has a mark feature). The cause is glyf header bounding boxes, not outlines. Bold: all within 2 units. Italic: 722 within 2 units, 2 at 3-10, 116 over 10; worst 37 units, U+05D0+U+0312, where composite uni0312 has header yMin 1170 in the release (outline 1158) and 1133 in ours. The table gate does not examine this (probes/fallback_mark_offsets.py, runs/p2-proto/fallback_mark_offsets.txt).
- The lookup-placement babelfont change is emulated (probes/mark_lookups_after_marker.py on the .glyphs, then a real fontc build), not implemented in Rust. The fontc ignoreMarks=false effect is simulated on built fonts, not built.
- The prototype converter is upstream main 496e904 + PRs #91/#92/#93 (integration-ff-prs 17ea899) plus this unit's patch plus the next-provenance anchor-propagation filter. It lives only in scratch (worktree /home/fsanches/compartilhado/sfd-reland-scratch/cardo/bf-wt, binary sha256 1cb8cf3dbed35c39). None of it is upstream, so no landing may cite it.
- Lohit-Bengali gains its abvm mark writer from the marker fix. The shaping corpus here does not cover Bengali (its script list lacks it), so the effect is unmeasured; that belongs to the unit that owns Lohit.
- Italiana-Regular double kerning was traced to FontForge subtables 0 and 1 of one kern lookup holding the same pairs, which babelfont split into an FEA lookup plus Glyphs kerning. There is no fix proposal here, and it needs its own unit. Ultra-Regular's 260 differing pairs were not examined.
- head.flags differ (the release has FontForge's Apple bits 7 and 9). The gate accepts this as 'set by the build', and no shaper reads those bits.
